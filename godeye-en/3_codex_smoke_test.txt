Create a Smoke Test plan for this project.

IMPORTANT:
Assume that the <project_name>_summary.md file has already been created previously.
Before writing the plan, read that summary to understand the project, its stack, modules, main flows, and structure.

This task is ONLY to create a Smoke Test plan.
DO NOT modify code.
DO NOT fix issues.
DO NOT implement tests.
DO NOT create features.
DO NOT refactor.
DO NOT commit.
DO NOT perform a full audit.
DO NOT generate a correction plan.
DO NOT suggest improvements outside the Smoke Test scope.

Your goal is to create a practical, objective, executable checklist to quickly validate whether the project continues to work in its essential areas.

==================================================
1. SMOKE TEST OBJECTIVE
==================================================

Create a Smoke Test plan that validates the minimum and essential functioning of the project after changes, merges, builds, releases, or important modifications.

The Smoke Test must answer:

“Does the project open, run, and do the main flows still work?”

The plan must focus on:
- startup
- basic build
- main screens
- critical flows
- basic persistence
- essential permissions
- main integrations
- import/export, if any
- navigation
- empty states
- basic error states
- obvious regressions
- minimum expected behavior

Do not turn it into an exhaustive test.
Do not turn it into an audit.
Do not turn it into full QA.
Do not turn it into an infinite checklist.

==================================================
4. PLAN RULES
==================================================

The plan must be:

- clear
- direct
- executable
- organized by priority
- specific to the project
- based on the existing summary
- useful for manual execution or future automation guidance
- separated by platform when applicable
- free of unnecessary opinion
- free of feature suggestions
- free of code fixes
- free of deep audit content

Each test must contain:
- ID
- test name
- objective
- preconditions
- steps
- expected result
- execution type
- priority
- notes, if necessary

==================================================
5. PRIORITY CLASSIFICATION
==================================================

Classify each test as:

CRITICAL:
Test that validates whether the project opens, compiles, starts, or executes an indispensable main flow.

HIGH:
Important flow test that affects normal use if broken.

MEDIUM:
Secondary flow or important behavior, but not immediately blocking.

LOW:
Polish, less frequent flow, or complementary validation.

==================================================
6. EXECUTION TYPES
==================================================

Classify each test as:

MANUAL:
Must be performed by a person.

AUTOMATABLE:
Can become an automated test in the future.

COMMAND:
Can be validated by terminal command.

REAL DEVICE:
Must be validated on a physical device, specific emulator, real browser, real environment, or real hardware.

ENVIRONMENT:
Depends on server, API, database, file, sensor, permission, or external service.

A test may use more than one type.
